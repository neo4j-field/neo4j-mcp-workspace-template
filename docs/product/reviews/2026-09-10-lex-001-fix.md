# LEX-001 fix review — explicit page accounting

Date: 2026-09-10

## Root cause

Every lexical writer already persisted the physical PDF page count as
`Document.totalPages`. `list_documents` and `verify_lexical_graph`, however, exposed
only the number of materialized `:Page` nodes under the generic field `pages`.
PyMuPDF intentionally writes chunks directly and creates no `:Page` nodes, so a
valid PDF was misleadingly reported as having zero pages.

## Contract change

- `sourcePageCount` is the number of physical pages in the input PDF.
- `pageNodeCount` is the number of materialized Neo4j `:Page` nodes.
- Job progress uses `sourcePagesExpected`, `sourcePagesProcessed`, and
  `currentFileSourcePageCount`.
- The ambiguous public `pages` and `total_pages*` response fields were removed rather
  than retained as misleading aliases.

The persisted `Document.totalPages` property is unchanged, so existing graphs remain
readable. For legacy documents without that property, inventory falls back to
`pageNodeCount`.

## Evidence

- Deterministic fixtures cover PyMuPDF (`2/0`), Docling (`2/2`), and page-image
  (`2/2`) source-page/Page-node behavior.
- Lexical unit and workflow contract suite: 14 tests and 11 subtests passed,
  including a generated two-page PDF parsed by the real PyMuPDF worker.
- Isolated live Neo4j test called the real `list_documents` and
  `verify_lexical_graph` MCP tools for all three parser modes and passed.
- The live fixture was removed (`0` remaining nodes).
- The retained `golden-e2e-20260910` graph remained at 5 nodes and 8 relationships.

## Scope boundary and follow-up

This fix does not convert PyMuPDF to `ParsedDocument`, force the parsers through one
writer, or redesign relationships. The canonical parser contract and single-writer
migration remain deferred as `DOC-001` under ADR-001.

Restart the lexical MCP server before expecting the renamed response fields in an
already-running client session.
