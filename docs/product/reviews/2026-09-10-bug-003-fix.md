# BUG-003 extraction coverage fix — 2026-09-10

## Demonstrated root cause

Blank model content, invalid/truncated structured responses, and retry exhaustion
all became an ordinary empty `ChunkExtractionResult`. The extraction job then
incremented `chunks_completed` and could finish with `status=complete`. A legitimate
valid-empty extraction was therefore indistinguishable from a failed source unit.

The source query also returned only the post-skip selection, so status could not
distinguish all content-eligible sources from those selected for the current run.

## Fix

- Added explicit per-source outcomes: `success`, `empty`, and `failed`.
- Blank/invalid structured responses now trigger bounded retries; exhaustion records
  the attempt count and error instead of returning success-shaped empty output.
- Added coverage counters for eligible, selected, attempted, successful, empty,
  failed, and persisted source units.
- Failed source IDs and failure details are returned by `check_extraction_status`.
- Any exhausted source makes the final job status `failed` after independent work is
  processed and successful output is persisted.
- Persisted-source coverage is counted from `EXTRACTED_FROM` relationships tagged
  with the exact extraction timestamp.

## Improvement feedback

The per-source outcome contract should become shared extraction infrastructure rather
than remain implicit in extractor implementations. Follow-on provenance work should
persist a durable run/source status in Neo4j; current job status is in memory, and a
server restart still loses the failure ledger. That belongs with `EXT-002`,
`EXT-003`, and stage-local recovery work rather than BUG-003.

Valid-empty output is now visible but is not automatically treated as failure,
because a source may legitimately contain no schema-matching entity. Quality gates
can later define an allowed empty-rate threshold per workflow or schema.
