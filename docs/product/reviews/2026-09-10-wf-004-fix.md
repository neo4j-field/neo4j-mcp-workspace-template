## Canonical ontology schema

- `(:Ontology)-[:CONTAINS]->(:NodeType|:RelationshipType)`
- `(:Ontology)-[:DEFINES]->(:AliasMap|:Blocklist)`
- `(:NodeType|:RelationshipType)-[:HAS_PROPERTY]->(:PropertyDef)`
- `(:RelationshipType)-[:FROM]->(:NodeType)`
- `(:RelationshipType)-[:TO]->(:NodeType)`
- `(:PropertyDef)-[:USES_ALIAS_MAP]->(:AliasMap)`
- `(:PropertyDef)-[:USES_BLOCKLIST]->(:Blocklist)`
- `(:AliasMap)-[:HAS_ALIAS]->(:Alias)`
- `(:Blocklist)-[:HAS_TERM]->(:BlockedTerm)`

The original mismatch was two Desktop-only ownership relationship names for node
and relationship types, while `ontology_loader.py` reads both through
`:CONTAINS`. The skill queries had already been corrected during the contract
repair pass; WF-004 closes the remaining gap by making that correction executable
and regression-tested rather than relying on string checks alone.

## Live-server limitation found

The restarted Codex entity MCP exposes both ontology tools, but its default
ontology database is `ontology`; that database does not exist in this DBMS, so a
direct `setup_ontology_db` call fails with `DatabaseNotFound`. The executable test
therefore instantiated the same server implementation with
`ontology_database="neo4j"`, matching this workspace's configured database.

This does not invalidate the ontology relationship contract, but the generated
MCP configuration/default should align the entity server's ontology database with
the ontology Cypher endpoint. Treat that configuration alignment as follow-up
work; no generated MCP config was modified here.

## Improvement feedback

Keep one executable fixture as the source of truth for the Desktop ontology
examples. Static documentation checks catch spelling drift; the live fixture
catches valid-looking Cypher that the loader or schema compiler cannot consume.
